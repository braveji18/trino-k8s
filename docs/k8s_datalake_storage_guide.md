# 온프레미스 K8s 데이터레이크 스토리지 선정 가이드

> **대상 환경**: 온프레미스 · 순수 Upstream Kubernetes · 엔터프라이즈 데이터레이크/분석 플랫폼
> **워크로드**: 분석/데이터레이크 (대용량 처리량 중심)
> **평가 우선순위**: ① 성능(IOPS/처리량) ② HA/DR 안정성 ③ 운영 단순성 ④ 비용 효율
> **검토 후보**: VAST Data · WEKA · IBM Storage Scale · Dell PowerScale(구 Isilon)

# 1부. 스토리지 솔루션 비교 통합 정리

## 1.1 4사 한눈에 비교

| 구분 | Dell PowerScale (구 Isilon) | VAST Data | WEKA | IBM Storage Scale |
|---|---|---|---|---|
| 아키텍처 | 스케일아웃 NAS (OneFS) | 플래시 우선 분리형(DASE) | 병렬 파일시스템(SW) | 병렬 파일시스템(GPFS) |
| 포지셔닝 | AI/ML·빅데이터·NAS | AI·대규모 비정형 데이터레이크 | GPU 집약 고성능 공유 계층 | AI·HPC·고급 분석 글로벌 플랫폼 |
| 성능/처리량 | 높음 (올플래시 + NFS over RDMA) | 매우 높음, 선형 확장 | 최상위 IOPS·저지연 | 높음 (검증된 병렬 FS) |
| HA/DR | 성숙, CSM Replication 모듈 | 분리형으로 장애도메인 분리 | 견고 | 성숙, AFM 분산 캐싱 |
| 프로토콜 | NFS 전용 | NFS·S3·블록 | 파일 중심(+오브젝트 티어링) | POSIX·S3·NFS·SMB·CSI |
| K8s CSI/운영 | 전용 CSI(CSM), 운영 직관적 | CSI GA, Helm, 운영 단순 | CSI, 운영 단순~중간 | CSI 지원, 운영 난도 높음 |
| 라이선스/비용 | 상용, 기존 자산 시 유리 | 상용, 데이터리덕션으로 단가↓ | 상용, 프리미엄 | 상용, 라이선스 복잡 |

## 1.2 솔루션별 상세

### Dell PowerScale (구 Isilon)
- OneFS 기반 스케일아웃 NAS. 전용 CSI 드라이버(`dell/csi-powerscale`)는 CSM(Container Storage Modules) 제품군의 일부.
- **CSI는 NFS 전용** → RWX(ReadWriteMany) 공유 볼륨이 자연스러워 분석 워크로드의 다중 Pod 동시 접근에 적합.
- 동적 프로비저닝, 스냅샷, 클론, 볼륨 확장, 볼륨 헬스 모니터링(2.1.0+) 지원. CSM 모듈로 Authorization·Replication·Observability·Resiliency 확장.
- 최근 NFS over RDMA 지원으로 AI 학습 처리량 개선(F710/F910 올플래시 라인).
- 액세스 존별로 다수 StorageClass 구성 가능. SmartQuota 미사용 시 PVC 크기 초과 가능 → 용량 강제하려면 활성화 필요.
- 참고: Dell이 csi-powerscale를 클로즈드 소스 모델로 전환(액세스/문의는 Dell Support).
- **적합 시점**: 기존 Dell/PowerScale 자산 보유, NFS 파일 중심 데이터레이크.
- **제약**: NFS 전용이라 한 플랫폼에서 S3 오브젝트 통합 불가. 최상위 처리량 경쟁에서는 한 발 뒤.

### VAST Data
- 계층형 디스크 구조를 플래시 우선 분리형(DASE) 인프라로 대체 → 노드 추가 시 처리량이 선형 확장.
- 컴퓨트/스토리지 장애 도메인 분리로 노드 장애에 강함.
- CSI 드라이버 GA, Helm/kubectl 설치, NFS 기반 StorageClass → RWX 자연스러움. 스냅샷·mount option 등 지원.
- NFS·S3·블록 멀티프로토콜 → 데이터레이크의 파일/오브젝트 혼재 접근에 유리.
- 올플래시지만 데이터 리덕션으로 단가 완화.
- **적합 시점**: 일반 분석 데이터레이크(파일+S3 혼재), 운영팀 규모 보통. 4개 우선순위를 고르게 만족.

### WEKA
- 코어당 성능 확장형 병렬 파일시스템. 코어당 30,000 IOPS·400MBps 이상을 300μs 미만 지연으로 제공한다고 주장.
- GPU 집약 환경의 고대역폭 공유 데이터 계층에 초점. 콜드 데이터는 오브젝트 스토리지로 티어링.
- CSI 드라이버 제공, 운영 단순~중간.
- **적합 시점**: 워크로드가 사실상 GPU 학습/추론이고 성능이 절대 우선. 비용·세부 운영 부담 감수 가능 시.

### IBM Storage Scale (구 Spectrum Scale/GPFS)
- AI·HPC·고급 분석용 글로벌 데이터 플랫폼. 2025 Gartner 엔터프라이즈 스토리지 매직 쿼드런트 리더.
- POSIX·S3·NFS/SMB·CSI 멀티프로토콜 지원. NVIDIA GPUDirect Storage(GDS)로 파일시스템-GPU 직접 DMA 경로.
- AFM(Active File Management) 분산 캐싱으로 지리적 분산 클러스터·서드파티 NFS·오브젝트를 아우르는 통합 네임스페이스.
- **적합 시점**: 광범위 프로토콜·글로벌 네임스페이스 필수, 전담 스토리지 엔지니어 보유.
- **제약**: 운영 난도가 4사 중 가장 높고 라이선스 모델이 복잡.

## 1.3 우선순위 기준 권고

- **종합 1순위 — VAST Data**: 성능(선형 확장)·운영 단순성·멀티프로토콜의 균형이 가장 좋음.
- **성능 절대 우선 — WEKA**: GPU 학습/추론 중심이면 최상위 성능.
- **광범위 프로토콜·글로벌 네임스페이스 필수 — IBM Storage Scale**: 전담 엔지니어 전제.
- **기존 Dell 자산·NFS 파일 중심 — Dell PowerScale**: 안정적·직관적이나 S3 통합·최상위 처리량은 한 발 뒤.

> 문서상 우열보다 **실측이 결정적**. 후보 2~3개를 동일 조건에서 PoC 벤치마크할 것.

# 2부. PoC 벤치마크 체크리스트

## 2.0 PoC 목표와 성공 기준 (먼저 합의)

| 항목 | 정의 | 예시 목표값(팀이 확정) |
|---|---|---|
| 목표 처리량 | 집계 읽기/쓰기 대역폭 | 예: 읽기 ≥ 40 GB/s, 쓰기 ≥ 20 GB/s |
| 목표 IOPS | 소파일/메타데이터 부하 | 예: 4K 랜덤 읽기 ≥ 1M IOPS |
| 지연 SLA | p99 지연 한도 | 예: p99 < 2 ms(블록형) / < 5 ms(NFS) |
| 동시성 | 동시 접근 Pod/클라이언트 수 | 예: 500 PVC, 200 동시 Pod |
| 가용성 목표 | 노드 장애 시 RTO/RPO | 예: RTO < 60s, RPO = 0 |
| 합격선 | PoC 통과 최소 점수 | 예: 가중 종합 80/100 이상 |

**원칙**: 모든 후보를 *동일 하드웨어·동일 네트워크·동일 워크로드*로 측정한다. 한 가지라도 다르면 비교가 무효.

## 2.1 사전 준비 체크리스트

### 환경 통제 (모든 후보 동일하게)
- [ ] 동일 K8s 버전·노드 수·노드 스펙(CPU/RAM/NIC) 고정
- [ ] 네트워크 동일: 대역폭(100/200/400GbE), RDMA(RoCEv2/IB) 활성 여부 명시
- [ ] MTU/Jumbo Frame, 멀티패스, NUMA 핀닝 설정 통일
- [ ] 클라이언트(부하 생성) 노드와 스토리지 노드 분리 여부 통일
- [ ] 캐시 영향 제거: 테스트 간 페이지 캐시 드롭, 데이터셋 > 캐시 크기

### 후보별 배포 준비
- [ ] CSI 드라이버 버전·설치 방식(Helm/Operator) 기록
- [ ] StorageClass 정의 확보 (액세스 모드, 프로토콜, 파라미터)
- [ ] 멀티프로토콜 필요 시: NFS(RWX) + S3 엔드포인트 둘 다 구성
- [ ] 라이선스/평가판 발급 및 벤더 지원 채널 확보

### 데이터셋 준비 (데이터레이크 대표 패턴)
- [ ] 대용량 순차 파일 세트 (예: Parquet/ORC, 수백 GB~TB)
- [ ] 소파일 대량 세트 (메타데이터 부하용, 수백만 개)
- [ ] 혼합 세트 (대/소 혼재)

## 2.2 평가 항목과 가중치

> 가중치는 평가 우선순위 순서를 반영. 팀 상황에 맞게 조정.

| # | 평가 영역 | 가중치(예) | 핵심 측정 |
|---|---|---|---|
| 1 | 성능 | 40% | 처리량, IOPS, 지연(p50/p99), 메타데이터 |
| 2 | HA/DR | 25% | 장애 주입 시 RTO/RPO, 복제, 무중단 |
| 3 | 운영 단순성 | 20% | 설치/업그레이드/확장/관측성 난도 |
| 4 | 비용 효율 | 15% | $/GB·$/GBps, 데이터 리덕션, 라이선스 |

## 2.3 성능 벤치마크 시나리오 (가중치 1순위)

### 순차 처리량 (데이터레이크 핵심)
- [ ] 대용량 순차 읽기 — 집계 대역폭 측정
- [ ] 대용량 순차 쓰기 — 집계 대역폭 측정
- [ ] 읽기/쓰기 혼합 (예: 70/30)
- 도구: `fio` (예: `--rw=read --bs=1M --numjobs=N --direct=1`), 또는 `elbencho`

### 랜덤 IOPS / 메타데이터
- [ ] 4K 랜덤 읽기/쓰기 IOPS
- [ ] 소파일 생성/조회/삭제 (메타데이터 ops/s) — `mdtest`
- [ ] 디렉터리 리스팅 지연 (대량 파일 디렉터리)

### 동시성/확장성
- [ ] 동시 클라이언트(Pod) 수 증가에 따른 처리량 곡선 (선형성 확인)
- [ ] 다수 PVC 동시 프로비저닝 시간 (예: 100/500 PVC 일괄 생성)
- [ ] RWX 공유 볼륨에 다중 Pod 동시 읽기/쓰기 정합성

### 실제 워크로드 (가장 중요)
- [ ] 실제 분석 엔진으로 대표 쿼리 실행 (Spark / Trino / Presto 등)
- [ ] TPC-DS 또는 사내 대표 쿼리 세트, 쿼리 완료 시간(wall-clock) 측정
- [ ] 객체(S3) 직접 접근 경로와 PVC(파일) 경로 각각 측정 (해당 시)
- [ ] GPU 학습 포함 시: 데이터 로딩 시간, 체크포인트 쓰기 시간

> 합성 벤치(fio/mdtest)는 비교 기준선용, **최종 판단은 실제 쿼리 시간**으로.

## 2.4 HA/DR 검증 시나리오 (가중치 2순위)

- [ ] 스토리지 노드 1대 강제 다운 → I/O 지속 여부, 회복 시간(RTO)
- [ ] 네트워크 링크 1개 차단 → 멀티패스 페일오버 동작
- [ ] 디스크/드라이브 장애 주입 → 리빌드 중 성능 저하 폭 측정
- [ ] K8s 워커 노드 장애 → PVC 재연결(특히 RWO 페일오버) 시간
- [ ] 스냅샷 생성/복원 정상성 및 소요 시간
- [ ] 복제(원격 사이트/클러스터) 구성 및 RPO 측정
- [ ] 업그레이드 중 무중단(rolling) 가능 여부

## 2.5 운영 단순성 평가 (가중치 3순위)

- [ ] 초기 설치 소요 시간·단계 수 (Helm vs Operator)
- [ ] CSI 드라이버/플랫폼 업그레이드 절차 난도
- [ ] 용량 확장(스케일아웃) 절차 및 무중단 여부
- [ ] 관측성: Prometheus/Grafana 연동, 볼륨 헬스 모니터링 지원
- [ ] StorageClass 다중 구성(테넌트/존 분리) 용이성
- [ ] 멀티테넌시·QoS·쿼터 설정 가능 여부
- [ ] 문서 품질 및 벤더 지원 응답성(티켓 응답 시간 실측)
- [ ] 장애 진단/로그 수집 편의성

## 2.6 비용 효율 평가 (가중치 4순위)

- [ ] 실효 용량 단가: $/유효 TB (데이터 리덕션 반영)
- [ ] 성능 단가: $/GBps, $/100K IOPS
- [ ] 라이선스 모델(용량 기반/노드 기반/구독) 및 3년 TCO
- [ ] 데이터 리덕션(중복제거/압축) 실측 비율
- [ ] 전력/랙 공간(밀도) — 데이터센터 제약 시
- [ ] 지원 계약(SLA 등급별) 비용

## 2.7 측정 도구 모음

| 목적 | 도구 |
|---|---|
| 처리량/IOPS/지연 | `fio`, `elbencho`, `vdbench` |
| 메타데이터/소파일 | `mdtest`, `IOR` |
| 분석 워크로드 | Spark, Trino/Presto, TPC-DS |
| 객체(S3) | `warp`, `s3-benchmark` |
| K8s 부하 분산 | Kubernetes Job/StatefulSet로 다중 Pod 동시 실행 |
| 관측 | Prometheus + Grafana, 벤더 CSI metrics |

> 모든 측정은 **3회 이상 반복**하고 중앙값·표준편차를 기록(분산이 크면 신뢰도 낮음).

## 2.11 최종 의사결정 체크

- [ ] 모든 후보가 동일 조건에서 측정되었는가
- [ ] 합격선(2.0 성공 기준)을 넘는 후보가 있는가
- [ ] 1순위(성능)에서 명확한 차이가 있는가, 측정 분산은 작은가
- [ ] 운영 인력 역량과 운영 난도가 부합하는가
- [ ] 3년 TCO가 예산 범위인가
- [ ] 벤더 지원/로드맵/레퍼런스(동종 업계) 확인했는가
- [ ] 락인 리스크(클로즈드 소스, 전용 HW 종속) 평가했는가
